# class_data: noisy call-center transcripts for classification and summarization

100,000 synthetic health-plan member-services calls generated by
`generate_class_data.py` for a proof of concept covering:

1. **Call classification** with a fine-tuned RoBERTa model
   * multi-class: `primary_label`, the main reason for the call
   * multi-label: `labels` / `label_vector`, every bucket substantively handled on the call
2. **Abstractive call summarization** with BART: `summary`

Transcripts use the same `agent:` / `customer:` speaker-turn format as
[`../auth_data/`](../auth_data/README.md) but are deliberately much noisier.
All names, companies, providers and numbers are fictional.

## Buckets

| Label | Covers |
|-------|--------|
| `BILLING` | premium invoices, payments, autopay, refunds, balances owed to the plan or a provider |
| `CLAIM_STATUS` | status, denial, reprocessing or appeal of a submitted claim |
| `COVERAGE` | whether a service, drug or provider is covered; deductible, copay, network, referral questions |
| `COMPLAINTS` | dissatisfaction with the plan, a provider, a vendor or a prior interaction; grievances; supervisor requests |
| `PRIOR_AUTH` | prior authorization requests, status, denials, expedited review, peer-to-peer |
| `NEMT` | non-emergency medical transportation: scheduling, cancelling, late/no-show rides, mileage reimbursement |
| `TECHNICAL_ISSUE` | member portal / mobile app login, password, ID card download, errors, missing data online |

`labels.json` holds the fixed label order used by `label_vector`.

## Files and splits

| File | Calls | Size |
|------|------:|-----:|
| `train.jsonl` | 80,001 | 118 MB |
| `validation.jsonl` | 10,000 | 15 MB |
| `test.jsonl` | 9,999 | 15 MB |
| `sample.jsonl` | 200 | 0.3 MB (first 200 calls, for quick inspection) |

The three split files are **git-ignored** because of their size; regenerate them
with the command below (deterministic, about 20 seconds). Splits are stratified
by `primary_label`, with no call shared across splits and no exact-duplicate
transcripts anywhere in the dataset.

Primary-label mix (train): Billing 21%, Claim Status 18%, Coverage 17%,
PriorAuth 13%, NEMT 11%, Complaints 10%, Technical Issue 10%. Labels per call:
one 55%, two 35%, three 10%. Secondary topics follow realistic affinities
(Billing+Claim Status, Coverage+PriorAuth, Billing+Technical Issue, Claim
Status+Complaints are the most common pairs). Full counts are in `stats.json`.

## Record schema

```json
{
  "id": "call_000311",
  "transcript": "agent: member services sofia speaking [baby crying] can i help customer: hi i need some help ...",
  "primary_label": "COVERAGE",
  "labels": ["COVERAGE", "PRIOR_AUTH"],
  "label_vector": [0, 0, 1, 0, 1, 0, 0],
  "summary": "Member Daniel Welch called evergreen health plan member services. Member asked whether an allergy test is covered; agent confirmed coverage under the select epo and explained the cost share. Member inquired about a prior authorization for trulicity from lakeside orthopedics, which was denied because the clinical criteria weren't met; agent explained appeal and peer-to-peer options. Outcomes: benefits explained; auth denied, appeal options given.",
  "noise_level": "medium",
  "n_turns": 19,
  "n_words": 171,
  "roberta_tokens": 223,
  "split": "train"
}
```

`roberta_tokens` is the exact `roberta-base` token count including special
tokens. BART uses the same byte-level BPE vocabulary, so the count applies to
the summarizer input too. Every transcript is under 512 tokens (train p50 196,
p90 294, max 488), so nothing is truncated with `max_length=512`. Summaries
run 26 to 138 BART tokens (p50 51), so `max_target_length=160` is safe.

## How calls are built

Each call is assembled from an opening (IVR fragments, greeting, usually a
brief ID / date-of-birth verification), a full exchange for the primary topic,
optional shorter add-on exchanges for one or two secondary topics ("oh and
while I have you..."), occasional unlabelled frustration remarks, and a close.
Each bucket has 5 to 7 sub-scenarios (for example Claim Status: pending,
denied with a reason, paid, pended for records, not on file) with randomized
facts: claim and authorization numbers, dates of service, amounts, providers,
drugs, procedures, pickup addresses, trip numbers, error codes.

The **summary** is generated from those underlying facts and the agent action
actually taken, in clean prose, so it is a faithful reference even when the
noisy transcript garbles a name or number. Dollar amounts are normalized to
`$123.45` in summaries.

## Noise

Each call draws a `noise_level` (low 30%, medium 45%, high 25%) that sets the
rates for:

* ASR confusions and homophones (`prior` -> `pryor`, `authorization` -> `author ization`, `deductible` -> `the ductible`, `ozempic` -> `o zempic`, `to`/`too`/`two`, ...)
* dropped short function words, stuttered repeats, fillers (`um`, `like`, `you know`)
* `[inaudible]`, `[crosstalk]`, `[background noise]`, `[static]`, `[hold music]` tags
* garbled numbers (digits spoken, regrouped, or split)
* truncated turns (`-- `, `[cut off]`), dropped calls at the end
* dropped speaker tags, so an utterance merges into the previous speaker's turn (diarization error)
* IVR fragments at the start, hold interruptions, transfers to the transportation line

Labels and summaries are not corrupted. If label noise is wanted for
robustness experiments, add it downstream so the clean labels remain available
for evaluation.

## Regenerating

```bash
uv run python class_data/generate_class_data.py                         # 100k calls, seed 20261014
uv run python class_data/generate_class_data.py --n 5000 --seed 7       # smaller set
uv run python class_data/generate_class_data.py --tokenizer none        # skip token counting
```

Token counts come from the local tokenizer at `/Users/sam/models/roberta-base`
(pass any HF name or path with `--tokenizer`). Calls that exceed `--max-tokens`
(default 512) are regenerated; none were needed for the shipped run.
